# Revision schema and preservation plan

The revised system retains `customers`, `employees` and `admins`, including their primary keys, profile fields and password hashes. It adds a `users` registry with a unique `(account_type, legacy_id)` pair pointing to those profiles, a trusted role, an optional department and an active flag. Existing credentials are not copied or reset. Because the profile reference spans three legacy tables it is validated by the account service; operational references use ordinary foreign keys to `users.id`.

New tables: `roles`, `departments`, `users`, `products`, `services`, `bookings`, `technician_assignments`, `attendance_logs`, `service_reports`, `notifications`, `announcements`, `payments`, `support_tickets`, `audit_logs`, `equipment_issues` and `settings`. Each operational row references the owning user and related booking/assignment where applicable. Accounts are deactivated rather than deleted. Department membership does not grant a role. Existing HR assignments are carried forward from the trusted configuration.

The exact additive changes and initial reference data are in `app/Database/Migrations/2026-10-20-150000_ManagementFoundation.php`. It refuses to overwrite already-existing target tables. The eight departments, six roles and seven documented service categories are reference data; no products, prices, stock, bookings, payments, reviews or operational statistics are fabricated. Existing profiles are registered without reading/copying password values. Rollback is deliberately blocked to avoid deleting operational records.

Customer requests begin as `requested`. Authorized dispatch/admin staff schedule a future appointment and assign an active technician with no overlapping two-hour visit. Technician check-in requires the assignment and either browser-provided coordinates or an explicit manual location reason. A service report after check-in completes the job; optional check-out remains available. Cancellation and rescheduling notify affected users and preserve history through audit records. Customer data, tickets, receipts, notifications and bookings are restricted by ownership on the server.

The migration is validated on isolated SQLite before use against the existing MySQL database. Database changes remain additive; no reset, drop or destructive rollback is part of installation. Review the migration and take a normal database backup before running it on another installation. Production deployment and Git publication remain separate from local implementation.
